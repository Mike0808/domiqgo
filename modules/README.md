# modules/ — целевая структура Domiq

Скелеты девяти модулей, созданные шагом **A1** плана миграции
([04-migration-plan.md](../docs/architecture/04-migration-plan.md)): пакеты
заведены заранее, чтобы контракты границ включились **до** появления первой
строки, а не после.

Наполнены три: [`tariffs/`](tariffs/) (шаг **C1**), [`metering/`](metering/)
(шаг **C2**), [`properties/`](properties/) (шаг **C3**) и
[`identity/`](identity/) (шаг **C4**, в работе). Все четыре — листья графа
зависимостей, и на них этап C заканчивается. Tariffs — образец формы: всё, что выделяется дальше,
повторяет его расположение слоёв, устройство `apps.py` и адрес миграций.

Properties показывает третье состояние — выделение может быть **частичным**:
таблица уже принадлежит модулю, но на неё ещё смотрят внешние ключи
устаревающего слоя, и разорвать их можно только шагами, до которых план не
дошёл. Такое состояние законно, если записано.

Metering показывает, что форма заполняется не сразу. На шаге переноса у него
есть `infrastructure/`, `api/` и словарь в `domain/`, но нет ни агрегата, ни
событий: правила приезжают отдельным шагом, потому что перенос кода и
изменение поведения не совмещаются (правило 7.4). Пустой `events/` и `domain/`
без инвариантов — не недоделка, а честное состояние незаконченного переезда.

## Слои внутри модуля

| Слой | Назначение | Ограничение |
|---|---|---|
| `api/` | публичный API: команды и запросы | единственная точка входа для чужих модулей |
| `events/` | контракты доменных событий | импортируются другими модулями наравне с `api/` |
| `domain/` | правила и инварианты | не импортирует django, requests, allauth — только stdlib |
| `application/` | оркестрация: команда → domain → repository → событие | не обращается к ORM |
| `infrastructure/` | Django-модели, ORM, внешние адаптеры | единственное место, знающее о базе |

## Модуль как Django-приложение

Django ждёт модели в `<пакет>/models.py`, а правило 3.2 держит их в
`infrastructure/`. Мирит это `AppConfig` модуля:

- `label` задаётся явно — иначе меткой станет последний сегмент пути
  (`tariffs` совпал бы случайно, `modules.billing` столкнулся бы с
  действующим `billing`);
- `import_models` переопределён и подставляет `infrastructure.models`;
- `ready()` импортирует `infrastructure/admin.py`;
- миграции лежат в `infrastructure/migrations/`, адрес объявлен в
  `MIGRATION_MODULES` (`config/settings.py`). Каталог `<модуль>/migrations/`
  роняет `test_orm_only_in_infrastructure` — и роняет правильно: миграция это
  ORM. Исключений в архитектурные тесты не вносилось.

Образец — [`tariffs/apps.py`](tariffs/apps.py).

## Правила границ

- Модуль не импортирует внутренности другого модуля: ни `domain/`, ни
  `application/`, ни `infrastructure/`. Разрешены только `api/` и `events/`.
- Cross-module ForeignKey запрещён в новом коде: ссылка на чужую сущность —
  по идентификатору, без констрейнта.
- JOIN на таблицы чужого модуля запрещён; чужие данные для чтения — через его
  Query Service.

Проверяется автоматически: [`.importlinter`](../.importlinter) и
[`tests/architecture/`](../tests/architecture/).

## Что здесь пока не так

**`billing/` существует дважды.** Есть действующее Django-приложение
`billing/` в корне (весь сегодняшний код) и пустой `modules/billing/` — целевой
модуль. Как пакеты Python они не конфликтуют, но когда `modules.billing`
станет Django-приложением, его метка по умолчанию совпадёт с меткой
существующего. К тому моменту метку нужно задать явно в `AppConfig` либо
расформировать старое приложение раньше — см. §2 плана миграции.

**`billing/` выведен из-под контрактов границ.** Он объявлен устаревающим
слоем и проверке не подлежит до расформирования: иначе контракты краснели бы
с первого дня и их пришлось бы отключить.

**Documents скелета не имеет.** Бриф фиксирует его границу, но детально не
проектирует; пакет появится вместе с реализацией.

## Чего здесь нет и не будет

**Шины событий.** Она живёт в корневом пакете [`bus/`](../bus/__init__.py), а не
здесь: у неё нет ни агрегата, ни инвариантов, ни своих данных, и десятый каталог
без всего этого обесценил бы слово «модуль»
([ADR-0027](../docs/architecture/adr/0027-event-bus-lives-outside-modules.md)).
Состав `modules/` охраняется тестом
`test_no_unexpected_top_level_packages`: он требует совпадения с картой, так что
завести здесь что-то мимо девяти нельзя, не тронув тест.

Модули знают о `bus`, `bus` не знает ни о ком — контракт
`bus-knows-no-domain`. Публиковать разрешено только из `application/`
(правило 4.4).
