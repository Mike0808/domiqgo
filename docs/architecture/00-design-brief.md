# Domiq — Design Brief (v2, brownfield)

Ты — Principal Software Architect и DDD-эксперт уровня Eric Evans / Vaughn Vernon.

Мы НЕ проектируем с нуля. Проект уже существует и работает.
Задача — спланировать переработку существующего кода в Modular Monolith
без остановки текущей функциональности.

Не писать код бизнес-логики. Разрешённые артефакты каждой фазы указаны явно.

---

## О ПРОЕКТЕ

**Название:** Domiq

**Что есть сейчас (as-is):**
Приложение для расчёта оплаты аренды:
- арендатор видит статус платежей (оплачено / не оплачено)
- тарифы: какой тариф, сколько стоит
- потребление: сколько потреблено по счётчикам
- начисления на основе тарифа и потребления

**Целевая аудитория (в порядке приоритета):**
1. Частные собственники с 2–3 квартирами, которым надоел Excel — ЯДРО
2. Мелкие инвесторы (до ~10 объектов)
3. Управляющие компании, апарт-отели, девелоперы — ТОЛЬКО как проверка
   расширяемости архитектуры, НЕ как источник требований к MVP

Следствие: архитектура должна быть эволюционируемой 10+ лет,
но объём функциональности первых итераций — уровня "замена Excel".
Модуль, не нужный собственнику с 3 квартирами, не проектируется детально —
для него фиксируется только место в карте и granица.

**Deployment:** Docker Compose (приоритет), Kubernetes, локальная установка.
**Стек:** Python, Django, PostgreSQL. Frontend не проектируем.
**Лицензия:** Open Source, Self-Hosted.

---

## ГЛАВНАЯ ЦЕЛЬ

Modular Monolith с чёткими границами модулей.
Не микросервисы. Не типовой Django-проект.
Любой модуль позже можно выделить в сервис почти без переписывания
бизнес-логики.

**Использовать:** DDD, Clean/Hexagonal Architecture, Vertical Slice,
SOLID, CQRS (только где это реально оправдано).

**Избегать:** God Objects, Anemic Domain Model, shared-модели между
модулями, циклические зависимости, utils.py с бизнес-логикой,
Feature Envy, Big Ball of Mud, а также ПРЕЖДЕВРЕМЕННОЕ усложнение
под enterprise-аудиторию.

## ФАЗЫ

### Фаза 0 — Инвентаризация (as-is)

Артефакт: `docs/architecture/01-as-is.md`

1. Карта текущих Django-приложений и их реальных ответственностей.
2. Граф импортов: кто кого импортирует (модели, сервисы, views).
3. Все ForeignKey, пересекающие будущие границы модулей.
4. Где сейчас живёт бизнес-логика (models / views / utils / signals /
   celery tasks) — по каждому значимому сценарию: расчёт начисления,
   фиксация показаний, определение статуса оплаты.
5. Список неявных контрактов: сигналы, общие константы, общие таблицы.
6. Ничего не оценивать и не предлагать — только факты со ссылками
   на файлы и строки.

### Фаза 1 — Целевая карта модулей (to-be)

Артефакты: `docs/architecture/02-target-map.md`,
по одному файлу на модуль в `docs/architecture/modules/`.

Отправная точка карты (изменяй, если обоснуешь):

| Модуль | Статус для ядровой аудитории |
|---|---|
| Identity | ядро (владелец + арендатор, роли) |
| Properties | ядро (квартиры, помещения) |
| Tenancy | ядро (кто живёт, период, условия — контракты и occupancy вместе, разделять рано) |
| Metering | ядро (счётчики, показания, потребление) |
| Tariffs | ядро (тарифы, версии тарифов, история цен) |
| Billing | ядро (начисления: тариф × потребление + фикс. платежи) |
| Payments | ядро (факты оплаты, статусы, сверка с начислениями) |
| Notifications | ядро-минимум (email/telegram "выставлен счёт", "просрочка") |
| Documents | граница зафиксирована, детально не проектировать |
| Maintenance | граница зафиксирована, детально не проектировать |
| Analytics | граница зафиксирована, детально не проектировать |
| Automation, AI, Finance | только место в карте |

Для каждого ЯДРОВОГО модуля:
- ответственность / что входит / что НЕ входит / почему
- публичный API: команды, запросы, события (имена и семантика, без кода)
- какие данные модуль владеет
- ubiquitous language модуля (глоссарий терминов)

Ключевые вопросы, на которые карта обязана ответить:
- Tariffs внутри Billing или отдельно? (история цен, версионирование)
- Metering отдаёт сырые показания или рассчитанное потребление?
- Кто владеет понятием "статус оплаты счёта" — Billing или Payments?
- Где граница между Tenancy и Billing (кому выставляется счёт)?

### Фаза 3 — План миграции (strangler)

Артефакт: `docs/architecture/04-migration-plan.md`

- порядок выделения модулей (начиная с наименее связанных)
- для каждого шага: что делаем, что НЕ трогаем, как проверяем,

Артефакты: `docs/architecture/05-rules.md`, `.importlinter`,

Перед оценкой сверься с docs/architecture/07-product-roadmap.md:

Артефакт: `docs/architecture/06-assessment.md`

## ПРАВИЛА ВЗАИМОДЕЙСТВИЯ МОДУЛЕЙ (рамка для фазы 1)

- Синхронный вызов чужого модуля — только через его публичный API
  (application layer), никогда через модели/ORM.
- Реакция на факт в другом модуле — Domain Event
  (пример: `MeterReadingRecorded` → Billing пересчитывает начисление).
- Чтение чужих данных для отображения — Query Service чужого модуля,
  а не JOIN на его таблицы.
- Одна база PostgreSQL, но каждый модуль владеет своими таблицами;
  схемы/префиксы таблиц по модулям.
- Domain layer не знает о Django ORM.

## ВАЖНО

- Каждое решение сопровождается "почему именно так".
- Каждая рекомендация проверяется вопросом: "нужно ли это собственнику
  с 3 квартирами прямо сейчас, или это задел — и тогда достаточно
  зафиксировать границу?"
- Фазы выполняются строго по очереди, каждая завершается артефактом
  и подтверждением человека.
