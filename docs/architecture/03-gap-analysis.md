# Domiq — Gap-анализ (Фаза 2)

Сопоставление инвентаризации ([01-as-is.md](01-as-is.md)) с целевой картой
([02-target-map.md](02-target-map.md)) и девятью спецификациями модулей.
Все ссылки — файл:строка на момент аудита.

Объём кода: 3 168 строк Python, из них 1 377 — тесты и 249 — миграции;
два Django-приложения, `billing` и `billing.esia_provider`.

---

## 0. Как читать классификацию

| Метка | Значение |
|---|---|
| **Л** | **Рвётся легко.** Правка в пределах одного-двух файлов, схема БД не меняется, наблюдаемое поведение не меняется. Откат — обратный коммит |
| **Ш** | **Нужен промежуточный шаг.** Разом переключить нельзя: требуется временная конструкция — двойная запись, адаптер, теневое поле — иначе система перестаёт работать между коммитами |
| **БД** | **Требует изменения схемы.** Миграция структуры, а иногда и данных: часть значений придётся синтезировать или спросить у владельца |
| **⚠** | **Меняется наблюдаемое поведение.** Пользователь заметит. Обязано попасть в план миграции отдельным пунктом и в примечания к релизу |
| **✔** | **Закрыто после аудита.** Пункт исправлен отдельным коммитом, не дожидаясь своего этапа; строка оставлена зачёркнутой, а не удалена, чтобы нумерация и ссылки из других документов не поехали |

## 3. Сводка по классам

| Класс | Пунктов | Что это значит для плана |
|---|---|---|
| **Л** — рвётся легко | 15 | Можно начинать в любой момент и в любом порядке; ни один не требует согласования с другими |
| **Ш** — нужен промежуточный шаг | 4 | №1 (перенос моделей), 21, 22, 35. Каждый требует временной конструкции |
| **БД** — требует изменения схемы | 17 | Из них четыре требуют не только структуры, но и **синтеза данных**: №6, 31, 32, 34 |
| **⚠** — меняется поведение | 9 | №6, 15, 16, 21, 29, 31, 32, 33, 35 |
| **✔** — закрыто после аудита | 1 | №9 (`PROTECT` вместо `CASCADE`, миграция `0007`) |

Сумма больше числа пунктов: №16 и №26 попадают в два класса каждый.

Из девяти помеченных ⚠ четыре проявятся один раз, при переходе (№6, 15, 32,
33), а **пять пользователь заметит в повседневной работе:**

1. **Блокировка ввода показаний смещается раньше** (№21, 35): сегодня показания
   правятся до появления платежа, в целевой модели — до выставления счёта.
2. **Выставление счёта становится отдельным действием** (№35): раньше счёт
   появлялся сам после ввода показаний.
3. **Удаление платежа заменяется отменой** (№16): запись и файл остаются.
4. **Один жилец на договор** (№31): в установке, где супруги входят по
   отдельности, второй потеряет доступ.
5. **Новая квартира с ГВС перестанет молча начислять ноль за подогрев**
   (№29): владелец, у которого норматив не заполнен, увидит требование его
   заполнить, а суммы в новых счетах вырастут.

Первые четыре — плата за правильные границы. Пятое — исправление ошибки,
но выглядеть оно будет как подорожание, и объяснять это придётся.

## 4. Обратный гап: чего в коде нет вовсе

Спецификации требуют понятий, которых сегодня не существует. Это не
нарушения — это работа, и для плана миграции она важнее нарушений, потому что
переносить тут нечего.

| Чего нет | Чей модуль | Замечание |
|---|---|---|
| **Период проживания** — ни даты заселения, ни даты выезда | Tenancy | Самое дорогое: даты не восстановить ни из чего, кроме памяти владельца |
| **Договор как сущность** | Tenancy | От него зависит ключ счёта (№6) |
| **Сумма платежа** | Payments | Сегодня чек — только фотография, поэтому частичная оплата невыразима |
| **Ручная отметка «оплачено» владельцем** | Payments | **Роадмап относит её к P1**, но платёж может создать только жилец через бота (`bot.py:46`); значение `web` в `SOURCE_CHOICES` объявлено и не используется |
| **Выставление счёта и срок оплаты** | Billing | Без них нет ни уведомления, ни просрочки |
| **Ревизии счёта** | Billing | Требование [ADR-0005](adr/0005-retroactive-tariff-correction.md) |
| **Замок периода как самостоятельное понятие** | Metering | Сегодня выводится из статуса счёта |
| **Журнал согласий** | Identity | Есть только последнее (№34) |
| **Адрес объекта** | Properties | Есть только метка для владельца; отчёту бухгалтеру её мало |
| **Проактивные уведомления, очередь, журнал доставки** | Notifications | Система не отправляет по своей инициативе ни одного сообщения; единственная исходящая связь — ответ бота на реплику (`bot.py:63`) |
| **Электронная почта** | Notifications | Ни настроек `EMAIL_*`, ни единого вызова отправки письма |
| **Любые выгрузки** | Reporting | Ни XLSX, ни CSV, ни JSON. Сегодня «выгрузить для бухгалтера» — это скопировать руками в Excel |
| **Доставка доменных событий** | все | Ни сигналов Django, ни Celery, ни шины: событий в проекте нет как явления |

Последняя строка стоит отдельного внимания: **вся событийная часть целевой
архитектуры не имеет в коде ни одного прообраза** — ни сигналов, ни очереди,
ни хотя бы места, куда её вставить. Это не мешает: синхронная внутрипроцессная
доставка после коммита проста. Но означает, что весь каталог событий целиком
относится к разделу «построить», а не «перенести», и что первым делом придётся
завести сам механизм — его отсутствие блокирует реакции всех модулей сразу.

## 5. Что из этого следует для фазы 3

Здесь только наблюдения; сам порядок — предмет плана миграции.

**Начинать можно с четырёх модулей одновременно.** Identity, Properties,
Metering и Tariffs не обращаются ни к кому. Из них у Tariffs меньше всего
связей с остальным кодом: `Tariff` не имеет ни одного FK, и его выделение не
задевает ни одной чужой таблицы.

**Пятнадцать пунктов класса Л не блокируют ничего** и делаются параллельно с
чем угодно — в том числе прямо сейчас, до начала переноса моделей.

**Три узла сцеплены между собой и разъезжаются только вместе:** ключ счёта
(№6), исчезновение `MonthlyStatement.status` (№15) и появление суммы у платежа.
Ни один из трёх не имеет смысла без двух других, а вместе они образуют
единственный по-настоящему крупный шаг миграции.

**Один пункт стоит сделать вне очереди.** №33 — владелец не может привязать
себе OAuth — это работающий дефект, а не долг архитектуры, и чинится он
переносом согласия на учётную запись, который всё равно предстоит.

## 6. Три вывода

1. **Нарушений границ меньше, чем ожидалось, и почти все они одного рода.**
   Пятнадцать пунктов рвутся правкой в одном-двух файлах. Причина в том, что
   проект мал и написан аккуратно: нет ни сигналов, ни raw SQL, ни фоновых
   задач, а `calculation.py` уже сегодня представляет собой чистый домен без
   ORM. Big Ball of Mud здесь не сложился — сложилось отсутствие границ, что
   лечится куда дешевле.

2. **Основная работа — не разделение, а достройка.** Тринадцать понятий из
   целевой карты в коде отсутствуют полностью, включая период проживания,
   сумму платежа, выставление счёта и всю событийную механику. План миграции
   будет не столько планом переноса, сколько планом строительства с
   аккуратным переносом того немногого, что уже есть.

3. **Самый дорогой пункт — не технический.** Ключ счёта по договору (№6)
   требует договоров, которых нет, а их даты неоткуда взять, кроме как
   спросить владельца. Это единственное место, где миграция упирается не в
   код и не в схему, а в данные, существующие только в голове пользователя, —
   и планировать его нужно как диалог с ним, а не как скрипт.
