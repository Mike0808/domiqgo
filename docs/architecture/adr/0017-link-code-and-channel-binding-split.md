# ADR-0017: Погашение кода привязки и привязка канала — две команды двух модулей

**Статус:** accepted
**Дата:** 2026-08-11
**Затрагивает модули:** Identity, Notifications
**Источник:** открытый вопрос №2 спецификации Identity и №1 спецификации
Notifications

## Контекст

Жилец пишет боту `/start <код>`, и система должна понять, чья это учётная
запись, а затем запомнить, что сообщения ему следует слать в этот чат. Сегодня
обе задачи решает одна функция `link_chat` (`linking.py:13-24`): находит
жильца по коду, записывает платформу и идентификатор чата, гасит код.

`02-target-map.md` §4 называет целевую команду `Identity.LinkChannel`, то есть
возлагает и то и другое на Identity. Та же карта в §2 при этом уже делит
`services/linking.py` между Identity и Notifications — то есть противоречит
сама себе.

## Решение

Команда разделяется на две:

1. `Identity.RedeemLinkCode(код)` — гасит одноразовый код и возвращает, какой
   учётной записи он принадлежал.
2. `Notifications.BindChannel(account_id, платформа, адрес)` — привязывает
   адрес канала к учётной записи.

Оркеструет их интерфейсный слой бота — тот, кто разобрал входящее сообщение.

## Обоснование

- Код доказывает личность: это утверждение о том, кто человек. Идентификатор
  чата — адрес доставки, к личности отношения не имеющий. Разные утверждения
  принадлежат разным модулям.
- Иначе Identity начинает хранить платформу и идентификатор чата, то есть
  знать про мессенджеры, — и модуль аутентификации приобретает транспортные
  подробности.
- Разделение согласуется с таблицей §2 карты, которая уже развела поля
  `Tenant.link_code` (Identity) и `Tenant.messenger_platform`,
  `messenger_chat_id` (Notifications).

## Отвергнутые альтернативы

- **Одна команда `Identity.LinkChannel`, как в карте.** Удобнее вызывающему —
  один вызов вместо двух, — но переносит адрес доставки в Identity.
- **Одна команда `Notifications.BindChannelByCode`.** Симметрично неверна:
  тогда Notifications проверяет одноразовый код, то есть занимается
  подтверждением личности.

## Следствия

- `Notifications.BindChannel` **не проверяет существование учётной записи.**
  Вызывающий только что получил идентификатор от Identity, погасив код; ещё
  одна проверка потребовала бы зависимости Notifications → Identity ради уже
  выполненной работы. Это сознательное доверие вызывающему, и его следует
  назвать в правилах фазы 4.
- Между двумя командами возможен сбой: код погашен, канал не привязан. Жилец
  окажется без канала и с недействительным кодом. Владелец обязан иметь
  возможность выпустить новый код — команда `IssueLinkCode` для этого и
  существует.
- Миграция разводит три поля `Tenant` по двум модулям
  ([03-gap-analysis.md](../03-gap-analysis.md), §2.3, п. 26).

## Триггеры пересмотра

- Появление второго способа подтвердить владение каналом (например, кода,
  присылаемого на почту): сценариев станет больше, и оркестрацию, возможно,
  придётся вынести в явный прикладной сервис вместо обработчика бота.
