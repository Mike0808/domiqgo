# ADR-0002: Плагинная модель роста — "Lego из модулей" (open core)

**Статус:** accepted (принципы), proposed (механика — уточнить в P2)
**Дата:** 2026-07-28
**Фазы роадмапа:** заложить границы в P1, инфраструктура в P2, монетизация в P3

## Контекст

Стратегия продукта: бесплатное open source ядро для частного
собственника (P1) + платные расширения для выросших аудиторий
(P2–P3). Пользователь собирает свою конфигурацию как Lego:
базовая версия бесплатна, более сложные возможности — плагины
за дополнительную цену.

Ключевой вопрос: что является единицей "плагина" и как это
совместить с modular monolith и open source лицензией.

## Решение

**Плагин = модуль (или пакет модулей) из целевой карты.**
Никакой отдельной "плагинной системы" рядом с модульной —
это одна и та же система границ.

### Три яруса поставки

| Ярус | Модули | Лицензия / цена |
|---|---|---|
| Core (бесплатно, open source) | Identity, Properties, Tenancy, Metering, Tariffs, Billing, Payments, Notifications | AGPL или аналог |
| Plus-плагины (P2) | Analytics, Documents, банковская сверка (расширение Payments) | платные, отдельные пакеты |
| Pro-плагины (P3) | Maintenance, Automation, платёжные шлюзы, мультиорганизации (расширение Identity) | платные, отдельные пакеты |

### Механика (принципы)

1. **Обнаружение:** плагин — python-пакет с entry point
   (`domiq.plugins`). Установлен пакет → модуль регистрируется:
   его подписки на события, его команды/запросы, его миграции,
   его пункты меню.
2. **Ядро не знает о плагинах поимённо.** Ядро публикует события
   и предоставляет extension points (навигация, дашборд-виджеты,
   хуки биллингового цикла). Плагин подписывается. Импорт из
   ядра в плагин — разрешён (public API); из ядра в плагин — запрещён.
3. **Отключаемость = тест границ.** Система обязана полноценно
   работать при отсутствии любого плагина. Если удаление пакета
   Analytics ломает Billing — граница спроектирована неверно.
4. **Данные:** таблицы плагина — его собственные (свой префикс/схема),
   при удалении плагина ядро продолжает работать, данные плагина
   остаются в БД инертными.
5. **Лицензирование платных плагинов:** self-hosted реальность —
   технически скопировать пакет можно всегда. Не строить DRM.
   Модель: лицензионный ключ проверяется мягко (плагин работает,
   пишет уведомление при невалидном ключе) + ценность в обновлениях
   и поддержке. Жёсткая проверка — только для SaaS-версии, если
   она появится.

### Что делается в каждой фазе

- **P1 (сейчас):** НИКАКОЙ плагинной инфраструктуры. Только чистые
  границы модулей и события — они и есть будущие extension points.
  Единственное дополнительное требование к P1: события Billing/
  Payments/Tenancy проектируются так, чтобы Analytics и Automation
  могли построиться снаружи (уже зафиксировано в роадмапе, п.2).
- **P2:** первый плагин — Analytics. На нём строится минимальный
  механизм: entry points, регистрация, изоляция миграций.
  Analytics намеренно выбран первым: он read-only (только Query
  Services и события), значит ошибка в механике не портит данные ядра.
- **P3:** плагины, изменяющие поведение (Automation, шлюзы) —
  добавляются hook points с явными контрактами.

## Обоснование

- Модуль как единица плагина — нулевая дополнительная архитектура:
  правила ADR-совместимости, независимости и владения данными
  уже требуются брифом. Плагинность — бесплатное следствие.
- Open core — проверенная модель для self-hosted
  (GitLab, Sentry, Metabase): ядро закрывает боль частника
  и растит сообщество, платят выросшие пользователи, у которых
  есть деньги и бизнес-потребность.
- Мягкое лицензирование — потому что аудитория self-hosted
  враждебна к DRM, а платящие P3-клиенты (УК, отели) покупают
  надёжность и поддержку, а не невозможность спиратить.

## Отвергнутые альтернативы

- **Feature flags в монолитном пакете** ("всё в одном, платное
  выключено флагом"): проще, но код платных фич лежит в open
  source репозитории — модель разваливается; и не тестирует
  границы отключаемостью.
- **Микросервисные плагины** (отдельные процессы): честная
  изоляция, но убивает простоту self-hosted деплоя P1
  и противоречит выбору modular monolith.
- **Marketplace сторонних плагинов с первого дня:** преждевременно;
  вернуться в P4.

## Триггеры пересмотра

- Первый сторонний разработчик хочет написать плагин → нужен
  стабильный версионируемый контракт extension points (semver).
- Появление SaaS-версии → пересмотреть механику лицензий.
- Если в P2 выяснится, что Analytics требует данных, недоступных
  через Query Services ядра → чинить границы ядра, не давать
  плагину прямой доступ к таблицам.

## Последствия

- (+) монетизация не требует отдельной архитектуры
- (+) отключаемость плагинов — постоянный автоматический тест границ
- (+) ядро остаётся маленьким и бесплатным — низкий порог входа
- (−) двойная дисциплина репозиториев (open core + приватные плагины)
- (−) миграции плагинов требуют аккуратного порядка применения
- (−) поддержка матрицы "ядро v X + плагин v Y" — нужна политика
  совместимости (зафиксировать при первом платном релизе)
