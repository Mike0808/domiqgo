# ADR-0008: Конфигурация объекта не версионируется

**Статус:** accepted
**Дата:** 2026-08-11
**Затрагивает модули:** Properties, Billing
**Источник:** открытый вопрос №4 спецификации Properties

## Контекст

Состав подведённых услуг и норматив подогрева ГВС ([ADR-0007](0007-gvs-heat-norm-ownership.md))
участвуют в расчёте счёта. Для тарифов принят обратный принцип: ставка
версионируется, и период считается по версии, действовавшей на его начало
([ADR-0004](0004-tariff-version-period-resolution.md)). Возникает вопрос,
почему конфигурация объекта живёт по другим правилам.

Опасность конкретна: сегодня admin-действие `regenerate_statements`
(`admin.py:54-68`) пересчитывает выбранные начисления по **текущей**
конфигурации квартиры. Отключив горячую воду и пересчитав прошлый месяц,
владелец молча получит счёт без строк ГВС.

## Решение

Состав услуг и норматив хранятся одним текущим значением, без истории.
Версионирование не вводится.

Защита обеспечивается не версионированием, а неизменяемостью выставленного
счёта: пересчёт исторического периода требует явного подтверждения человеком и
порождает ревизию ([ADR-0005](0005-retroactive-tariff-correction.md)).

## Обоснование

- Изменение конфигурации не может задним числом переписать выставленный
  документ — это уже гарантировано ADR-0005. Значит, версионирование добавило
  бы корректность только там, где она и так обеспечена.
- Частота изменений несопоставима с тарифной. Ставки меняются примерно дважды
  в год у всех сразу; состав подведённых услуг у собственника с тремя
  квартирами не меняется годами, а норматив вводится однажды.
- Второй механизм версионирования — это история изменений, выбор версии на
  дату и отдельный интерфейс просмотра. Бриф прямо называет такое
  преждевременным усложнением под enterprise-аудиторию.

## Отвергнутые альтернативы

- **Версионировать по образцу тарифных линий.** Дало бы корректный пересчёт
  любого прошлого периода без опоры на неизменяемость счёта. Отвергнуто по
  соотношению цены и частоты события.
- **Запретить изменение конфигурации при наличии выставленных счетов.**
  Гарантирует согласованность грубой силой, но делает невозможным обычное
  действие: провели горячую воду — отметить это надо, а счета за прошлые годы
  уже есть.

## Следствия

- Решение **опирается на ADR-0005 и без него неверно.** Если неизменяемость
  счёта когда-нибудь ослабят — например, ради массового пересчёта в P3, —
  исторические периоды начнут считаться по сегодняшней конфигурации, причём
  молча: в отличие от тарифа, у конфигурации нет ни даты, ни следа изменений.
  Обнаружить подмену будет нечем.
- Событие `PropertyServiceCompositionChanged` публикуется, но подписчиков в P1
  не имеет — оно существует ради будущего аудита и Analytics.

## Триггеры пересмотра

- Любое ослабление неизменяемости счёта.
- Появление начисления по нормативу при отсутствии прибора (P2): тогда
  конфигурация объекта начинает влиять на сумму сильнее, чем сейчас, и цена
  ошибки растёт.
- Первый случай, когда владелец не может объяснить расхождение между старым
  счётом и текущей конфигурацией.
